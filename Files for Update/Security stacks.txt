For your SparkIntellect setup, I would treat security as a production architecture, not as a few .env variables or a .gitignore file.

Your stack is:

Next.js → Netlify → Node.js backend → Render → MongoDB Atlas → Google Sheets/Drive → email provider

For this architecture, the goal should be:

Assume the frontend is public and potentially compromised. Keep every secret and every privileged operation behind the backend, enforce authorization server-side, minimize attack surface, and make a compromised component unable to compromise the rest of the system.

Below is the security architecture I would use.

1. First: what should NOT be in production?

There are several things I would deliberately avoid.

❌ Don't expose MongoDB to the frontend

Never:

Next.js → MongoDB

Always:

Next.js → Backend → MongoDB

The MongoDB connection string must never be sent to the browser.

❌ Don't put secrets in Next.js NEXT_PUBLIC_*

Anything beginning with:

NEXT_PUBLIC_

is potentially exposed to the browser.

So never do:

NEXT_PUBLIC_MONGODB_URI=
NEXT_PUBLIC_GOOGLE_CLIENT_SECRET=
NEXT_PUBLIC_RESEND_API_KEY=
NEXT_PUBLIC_JWT_SECRET=
NEXT_PUBLIC_DATABASE_PASSWORD=

These are serious mistakes.

Only genuinely public configuration belongs in NEXT_PUBLIC_*.

❌ Don't store authentication tokens in localStorage

Avoid:

localStorage.setItem("token", token)

for your admin authentication.

Prefer:

HttpOnly
Secure
SameSite

cookies/session mechanisms.

This significantly reduces the impact of many XSS scenarios.

❌ Don't use one shared admin account

Never:

admin@sparkintellect.in
password123

used by everyone.

Each employee gets their own account.

The CEO has a separate account.

❌ Don't give employees database access

Employees should never receive:

MongoDB username
MongoDB password
MongoDB URI

Their access goes through the Admin Panel → Backend.

❌ Don't give employees Render access unless absolutely necessary

Render access should be restricted to the technical owners.

An employee who only manages internships shouldn't have infrastructure access.

❌ Don't give employees GitHub repository write access unnecessarily

A recruitment employee doesn't need:

GitHub repository
Render
MongoDB Atlas
Netlify
Google Cloud

access.

Their only access should be:

admin.sparkintellect.in

with appropriate permissions.

❌ Don't allow arbitrary file uploads

Don't accept:

.exe
.php
.js
.html
.svg
.zip
.sh

as resumes unless there is an explicit business requirement and a proper security pipeline.

For your internship system, I'd initially accept:

PDF
DOC
DOCX

with strict size limits.

❌ Don't permanently delete important records

Don't let ordinary employees permanently delete:

Applications
Contact enquiries
Internships
Employees

Use:

Active
Inactive
Closed
Archived

instead.

Permanent destructive operations should be restricted heavily, ideally to the CEO and/or a controlled technical administrator.

6. WAF

Use a Web Application Firewall where appropriate.

The objective isn't:

"Block everything."

It's:

Block obviously malicious traffic before it reaches your application.

Rules can target:

SQL injection patterns
XSS patterns
malicious bots
suspicious requests
abusive IPs
excessive request rates

But don't depend solely on WAF.

Your application must still validate everything.

7. Cloudflare Turnstile

Use Turnstile on:

especially on public forms.

Architecture:

User
 ↓

 ↓
Turnstile token
 ↓
Backend
 ↓

 ↓
Accept / Reject

The backend must verify the token.

Never trust a CAPTCHA result supplied only by the frontend.

8. Rate limiting

This is essential.

At minimum protect:

POST /auth/login
POST /auth/forgot-password
POST /contact
POST /internships/:id/apply
POST /upload

For example, don't allow someone to make thousands of:

POST /contact

requests.

Use different limits for different endpoints.

Login

Very strict.

Contact

Moderate.

Internship applications

Moderate, with additional duplicate/spam detection.

Public GET requests

More relaxed.

9. Backend security headers

Your Node.js backend should send appropriate security headers.

Use a well-established security middleware such as Helmet where applicable.

Important headers include:

Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options
Referrer-Policy
Permissions-Policy

Be careful with CSP rather than blindly copying a configuration, because an overly restrictive CSP can break your legitimate Next.js scripts or integrations.

10. Content Security Policy

CSP is particularly useful against XSS.

Conceptually:

default-src 'self'
script-src 'self' trusted-sources
style-src 'self' trusted-sources
img-src 'self' https: data:
connect-src 'self' https://api.sparkintellect.in

But your exact CSP should be generated around the actual services you use.

Don't use:

script-src *

as a shortcut.

11. CORS

Your backend should explicitly allow only your websites.

For example:

https://sparkintellect.in
https://www.sparkintellect.in
https://admin.sparkintellect.in

Don't use:

Access-Control-Allow-Origin: *

for an authenticated admin API.

Use:

20. CSRF protection

If you use cookie-based authentication, carefully protect state-changing requests against CSRF.

Options include:

SameSite cookies
CSRF tokens where needed
Origin/Referer validation for sensitive operations
Proper CORS restrictions

Don't assume CORS itself is CSRF protection.

21. Input validation

Every API endpoint needs server-side validation.

Use:

Zod

or your backend framework's validation system.

For example:

email
phone
budget
internshipId

employee permissions

should all be validated.

Never trust frontend validation.

22. Prevent mass assignment

This is a subtle but important vulnerability.

Don't allow a request like:

{
  "name": "Arun",
  "role": "CEO",
  "permissions": ["*"]
}

to be blindly passed into MongoDB.

Explicitly decide which fields an endpoint is allowed to modify.

For example:

Employee update endpoint
allowed:
name
department
status

restricted:
role
permissions

Permission changes should have a separate protected endpoint.

23. MongoDB security

Don't use the Atlas owner account from your application.

Create a dedicated application database user with only the permissions it requires.

38. MongoDB injection

MongoDB doesn't have SQL injection in the same form as SQL databases, but untrusted query objects can still create serious problems.

Never blindly accept:

req.body

as a MongoDB query/filter/update.

Use strict schemas and sanitize inputs.

For example, an endpoint expecting:

status

should only accept:

new
reviewing
shortlisted
interview
selected
rejected

not arbitrary MongoDB operators.

39. API response security

40. Admin API should expose minimum data

50. GitHub secret scanning

51. If a secret is ever committed

This is critical.

Don't simply:

git rm .env

and assume the secret is safe.

Git history may still contain it.

Immediately:

Revoke credential
Generate new credential
Update production secret
Remove compromised credential

Then clean the repository history if necessary.

The secret is considered compromised once committed.

52. Never put secrets in GitHub Actions logs

Be careful with:

echo $SECRET

or debugging environment variables.

A secret can accidentally become visible in CI logs.

53. Dependency security

Your Next.js and Node.js projects will have many dependencies.

Regularly run:

npm audit

and keep dependencies updated.

But don't blindly run major upgrades directly in production.

Use:

 ↓

 ↓

 ↓

54. Lock dependencies

Commit:

package-lock.json

or the appropriate lockfile.

Use deterministic installs in CI.

This prevents "works on my machine" dependency differences.

55. Don't install unnecessary packages

Every dependency increases attack surface.

If you need:

date formatting

don't install a giant library unless necessary.

More packages = more potential vulnerabilities.

56. Keep Next.js updated

Your frontend framework should be kept on supported versions.

Security vulnerabilities can occur in:

57. Node.js production configuration

MongoDB Atlas should have automated backups enabled.

You should have a recovery strategy:

 ↓

61. Disaster recovery

72. Prevent IDOR

A major API vulnerability is:

Insecure Direct Object Reference.

Example:

Employee has access to application:

/application/123

They manually change:

/application/124

and see another restricted record.

Every backend request must verify:

Does this user have permission to access THIS resource?

Not merely:

Does this user have application.read?

This becomes especially important if later you introduce departments or scoped employee access.

For example:

Recruitment employee
→ Applications

Internship employee
→ Internship applications

Finance employee
→ Billing

74. Prevent privilege escalation

An employee must never be able to submit:

  "permissions": ["*"]
}

Even if the employee modifies the request manually, it must fail.

87. If the admin frontend is compromised

Your architecture should limit the damage.

Suppose someone compromises the admin frontend.

They still shouldn't automatically get:

Google credentials
Render credentials

because those are never in the frontend.

They would still have to defeat the backend's authorization.

This is why the architecture matters more than .gitignore.
