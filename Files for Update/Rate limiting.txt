rate limiting must be explicitly implemented. It should not be treated as an optional setting.

For your SparkIntellect architecture, I would make rate limiting part of the backend security layer, with different limits for different endpoints.

You want multiple layers, not one global rate limiter.

1. Public contact form

Endpoint:

POST /api/v1/public/contact

I'd use a relatively strict limit such as:

5 requests / 15 minutes / IP

combined with:

Cloudflare Turnstile

and server-side validation.

So a bot can't simply spam your company inbox.

2. Internship applications

Endpoint:

POST /api/v1/public/internships/:id/apply

For example:

3 applications / 15 minutes / IP

plus:

Turnstile
Duplicate application detection
Email validation
Request validation
File limits

You can also prevent repeated applications to the same internship using the same email address if that's part of your business rules.

3. Admin login

This deserves the strongest protection.

POST /api/v1/auth/login

For example:

5 failed attempts / 15 minutes / IP

But don't rely only on IP.

Also track:

IP
+
email/account
+
device/session characteristics

because an attacker can rotate IP addresses.

After repeated failures:

Login
 ↓
Too many attempts
 ↓
Temporary block / progressive delay
 ↓
Try again later

For the CEO account, I'd additionally require MFA.

4. Password reset

Endpoint:

POST /api/v1/auth/forgot-password

Very strict:

3 requests / hour / IP

And the response should always be generic:

If an account exists, a password-reset email will be sent.

Don't reveal whether an email belongs to an account.

5. Admin API

Authenticated APIs should also have limits.

For example:

GET requests
→ higher limit

POST/PATCH/DELETE
→ lower limit

But you shouldn't use a single arbitrary limit for everything.

Example concept:

GET /admin/internships
100 / minute / user

POST /admin/internships
20 / minute / user

PATCH /admin/internships/:id
30 / minute / user

DELETE /admin/internships/:id
10 / minute / user

These are starting points, not universal magic numbers. We'd tune them based on actual usage.

6. Employee-specific limits

Because your system has RBAC, rate limiting can use the authenticated user ID.

For example:

Employee A
 ↓
100 API requests/minute

while:

Employee B
 ↓
100 API requests/minute

The limits are independent.

This prevents one employee's activity from consuming the entire system's quota.

8. Cloudflare rate limiting

I'd also put rate limiting before the backend.

So:

Attacker
   ↓
Cloudflare
   ↓
Blocked

instead of:

Attacker
   ↓
Render
   ↓
Node.js
   ↓
Rate limiter
   ↓
Blocked

The first approach saves your backend resources.

Cloudflare can handle broad traffic-abuse rules, while your Node.js application handles business-specific limits.

9. Two-level rate limiting

This is what I'd recommend for your production setup:

                  INTERNET
                     ↓
                CLOUDFLARE
                     ↓
             IP / Bot limits
                     ↓
                NETLIFY
                     ↓
              Node.js API
                     ↓
           Application limiter
                     ↓
        ┌────────────┼────────────┐
        ↓            ↓            ↓
       IP          User ID      Endpoint

This is much stronger than simply:

100 requests / minute

globally.

10. Redis — do we need it?

For a production system with multiple backend instances, a distributed rate limiter is preferable.

You can use:

Redis

Architecture:

Node.js
   ↓
Rate Limiter
   ↓
Redis

Redis stores counters such as:

IP: 103.x.x.x
Endpoint: /contact
Count: 4
Window: 15 min

However, I wouldn't automatically introduce Redis just because it exists.

If your initial Render deployment has one backend instance, an in-process limiter can work initially, while Cloudflare handles edge protection.

If you later scale to multiple backend instances, move the application-level rate limiter to a shared Redis-backed implementation.

11. Important: rate limiting isn't authentication

This is a critical distinction.

Rate limiting says:

"You are making too many requests."

Authentication says:

"Who are you?"

Authorization says:

"Are you allowed to do this?"

You need all three.

Request
 ↓
Rate Limit
 ↓
Authentication
 ↓
Authorization
 ↓
Validation
 ↓
Business Logic
12. Don't rate-limit only by IP

This is a common mistake.

IP-only rate limiting can be bypassed with:

VPNs
Proxies
Botnets
Mobile networks

And it can unfairly affect users behind shared networks.

So use combinations such as:

IP
+
Account ID
+
Endpoint
+
Action

For unauthenticated forms:

IP
+
email
+
endpoint
+
Turnstile
13. Application-specific anti-spam

For internship applications, rate limiting alone isn't enough.

Consider:

Same email
+
Same internship
+
Repeated submissions

If someone submits the same application repeatedly, the backend can respond:

An application has already been received for this internship.

This also protects your Google Sheet and email systems.

14. Protect Google Sheets

This is another reason rate limiting matters.

Imagine a bot sends:

10,000 applications

Without protection:

10,000 MongoDB writes
10,000 Google Sheet API calls
10,000 emails

That's terrible.

With protection:

Bot
 ↓
Cloudflare
 ↓
Rate limit
 ↓
Turnstile
 ↓
Backend validation
 ↓
Most requests rejected

Only legitimate requests reach Google Sheets.

15. Protect email sending

Your contact endpoint is particularly dangerous because an attacker could use your API as an email-spamming service.

Never let:

POST /contact

directly translate into unlimited email sending.

Use:

Rate limiting
+
Turnstile
+
Validation
+
Duplicate detection
+
Email quotas
16. Queueing for external services

For higher reliability, I'd eventually use:

Application
 ↓
MongoDB
 ↓
Job Queue
 ├── Google Sheets
 └── Email

rather than making the HTTP request wait for everything.

But this is something I'd introduce when needed rather than unnecessarily complicating version 1.

17. Rate-limit response

When the limit is reached, return:

HTTP 429 Too Many Requests

and preferably a Retry-After header when you know the retry window.

Frontend can then display:

Too many requests. Please try again in a few minutes.

Don't expose internal rate-limiter implementation details.
