The cleanest way to understand the new SparkIntellect system is to treat it as 4 connected layers, each with a different responsibility:

┌──────────────────────────────────────────────────────────┐
│                    SPARKINTELLECT                        │
│                                                          │
│  1. FRONTEND     2. BACKEND     3. DATABASE     4. ADMIN│
│                                                          │
│  Netlify         Render         MongoDB Atlas   Admin UI │
└──────────────────────────────────────────────────────────┘

The most important rule is:

Frontend never talks directly to MongoDB. Admin never directly modifies the database. Everything goes through the Backend API.

2. What each layer does

This separation is extremely important.

Frontend

The frontend is responsible for:

Displaying the website
Showing internships
Showing services
Showing industries
Displaying forms
Collecting user input
Sending API requests
Showing success/error messages
Responsive/mobile experience
SEO/UI

It should not:

Store database credentials
Decide whether an employee is authorized
Directly modify MongoDB
Contain Google API credentials
Contain email provider secrets
3. Backend

The backend is the brain of the system.

It handles:

Authentication
Authorization
Permissions
Business logic
Validation
MongoDB operations
File uploads
Email
Google Sheets
Admin operations
Security
Audit logs

Everything important passes through here.

19. What if Google Sheets fails?

This is an important production consideration.

Don't make the application depend entirely on Google Sheets.

Correct workflow:

Candidate
   ↓
MongoDB
   ↓
Application successfully saved
   ↓
Try Google Sheets
   ↓
FAILED
   ↓
Mark sync = pending

Then retry later.

Example:

googleSheetSync:
{
   status: "pending",
   attempts: 2
}

So you never lose an application because Google had a temporary API problem.

28. Read-only employee

Employee opens an internship.

They can see:

Title
Description
Applications

But:

Create
Edit
Delete

are unavailable.

However, the real security is backend-side.

If they manually try:

POST /api/admin/internships

backend checks:

Does user have internship.create?

No.

Response:

403 Forbidden

So even if they manipulate the browser, they cannot create an internship.

39. Database relationship concept

For example:

 │
 └── createdBy → Internship

Internship
 │
 ├── applications
 │
 └── googleSheet

Application
 │
 └── internshipId → Internship

So:

Internship
   │
   ├── ID
   ├── Title
   ├── Form
   ├── Status
   └── Google Sheet ID
             │
             ↓
       Applications

45. Recommended API separation

I'd divide the API into:

/api/public/*

For public website.

/api/auth/*

For authentication.

/api/admin/*

For administrative functions.

For example:

PUBLIC

GET  /api/public/internships/:slug
POST /api/public/internships/:id/apply
POST /api/public/contact

Admin:

GET    /api/admin/internships

46. What happens when the backend is down?

Your public static pages can still potentially load if designed properly.

But dynamic functionality won't work:

Backend down
    ↓
Internship API unavailable
    ↓
Application unavailable
    ↓
Contact unavailable

Therefore production needs:

Monitoring
Error logging
Health checks
Database backups
Alerts
Graceful frontend errors

For example:

"We're temporarily unable to load internship opportunities. Please try again shortly."

rather than a broken page.

47. What happens when MongoDB is down?

Backend should fail gracefully.

Frontend
 ↓
Backend
 ↓
MongoDB unavailable
 ↓
503
 ↓
Frontend friendly error

You should also have:

MongoDB Atlas backups
Monitoring
Proper indexes
Connection pooling
Retry logic where appropriate

50. In your case, the ideal final system

I'd therefore build SparkIntellect around four clear products:

① Public Website
sparkintellect.in

Premium, simple, fast, SEO-friendly.

② Admin Portal
admin.sparkintellect.in

CEO + employee controlled.

③ Backend
api.sparkintellect.in

Node.js/TypeScript on Render.

④ Database
MongoDB Atlas

Central source of truth.

Then integrate:

Google Sheets
Email
File Storage
Analytics

around the backend.

The result is that the frontend becomes the presentation layer, the backend becomes the brain, MongoDB becomes the source of truth, and the admin panel becomes the control center. That separation will let you grow SparkIntellect's website without turning every content change into a coding/deployment task.
